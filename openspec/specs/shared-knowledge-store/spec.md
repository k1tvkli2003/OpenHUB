## Requirements

### Requirement: One canonical live knowledge repository serves every runtime

OpenHUB SHALL keep user-authored skills, durable memories, and global agent
instructions in `C:/Users/K1/.codex` as the single canonical content tree and
SHALL expose that tree to Codex, Hermes, and OpenCode through live links or
runtime loaders rather than copied mirrors.

#### Scenario: Canonical skill changes

- **WHEN** a canonical skill file changes under `C:/Users/K1/.codex/skills`
- **THEN** Codex, Hermes, and OpenCode observe the same changed bytes through
  their configured live entry points without running a copy/sync job

#### Scenario: Runtime has native resources

- **WHEN** Hermes or OpenCode already owns native skills, memory, configuration,
  or session data
- **THEN** federation preserves those resources and adds a distinct shared
  entry point instead of replacing the runtime-owned directory

#### Scenario: Sensitive stores are adjacent

- **WHEN** credentials, auth stores, provider configuration, MCP secrets,
  sessions, caches, or build outputs exist under or beside a runtime home
- **THEN** the federation exposes only the allowlisted skills, memories, and
  global instruction paths and does not copy or link sensitive stores

### Requirement: Transitional copies are retired safely

OpenHUB SHALL remove only resources proven by its manifest to be generated by
the previous copy implementation and SHALL preserve any target whose ownership,
path boundary, or content has changed.

#### Scenario: Generated file was modified

- **WHEN** an OpenHUB-owned copied file no longer matches its recorded source or
  manifest identity
- **THEN** conversion skips and reports that file rather than deleting or
  overwriting it

### Requirement: Applied Hermes federation activates its managed loader

When an operator applies shared-knowledge federation, OpenHUB SHALL explicitly
enable the managed `openhub-shared-knowledge` Hermes plugin so that current
Hermes opt-in plugin loading injects canonical instructions and memory into new
agent turns.

#### Scenario: Installed plugin was not previously enabled

- **WHEN** federation is applied and the managed plugin is absent from
  `plugins.enabled`
- **THEN** OpenHUB adds the managed plugin id to `plugins.enabled`
- **AND** a fresh Hermes process loads the plugin

#### Scenario: Managed plugin was explicitly disabled

- **WHEN** federation is applied and the managed plugin appears in
  `plugins.disabled`
- **THEN** OpenHUB removes only the managed plugin id from `plugins.disabled`
- **AND** preserves every unrelated disabled plugin

#### Scenario: Existing plugin choices are present

- **WHEN** Hermes already has unrelated enabled or disabled plugins
- **THEN** applying federation preserves those choices unchanged

#### Scenario: Federation is a dry run

- **WHEN** federation is evaluated without apply confirmation
- **THEN** Hermes plugin activation state is not changed
